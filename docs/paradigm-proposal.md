# Производительность sudachi.rs: две дороги бок о бок (для мейнтейнера)

> **Вердикт.** В рамках контракта совместимости sudachi.rs с Java-Sudachi: зашипить byte-identical-выигрыши
> — #39 + #40 (~+9%) **+ #52 (share `WordInfo` data+strings через Arc-cache, +27% на default-выводе,
> +44% на полном `-a`-выводе, byte-identical [meas, реальный словарь])** поверх prefetch+varint, **итого
> 1-thread потолок ≈ 1.4–1.6×** (выигрыш растёт с объёмом материализуемого вывода — делятся и декодированные
> строки; раньше оценка прототипа была +20–21%) — и взять **multithreading (~8.9×)** для throughput. Решёточное ЯДРО
> (`connect_node`/матрица) *доказуемо* на полу — не трогать; крупный рычаг нашёлся в материализации WordInfo
> (#52). Ускорение **~3.7×** реально и измерено, но только ценой отказа от совместимости (pointwise
> Vaporetto+dict: нет A/B/C, −0.92 SEG, −1.74 POS) — жизнеспособно как *отдельный* инструмент, никогда
> как sudachi.rs. **Рекомендация: Path A для библиотеки; Path B держать на полке как измеренную опцию.**

*Документ для принятия решения. Обе дороги ускорения sudachi.rs расписаны полностью, с плюсами и
минусами каждой, чтобы trade-off был виден и выбор — за вами. Каждое число скорости/качества — [meas]
на запускаемом артефакте (решётка: `tokenize_pipeline_bench`; pointwise: fused `/tmp/vapo-sud`;
golden-бенчмарк `/tmp/gold/`), Apple M4 Max, UD-Japanese-GSD. Полное исследование: `optimization-study.md`.*

## Вопрос и единственное ограничение, его обрамляющее

Насколько быстрее может стать токенизатор? Ответ расщепляется на одном вопросе:

> **Должен ли вывод оставаться идентичным Java-Sudachi** — та же A/B/C-мультигранулярность, те же POS,
> те же границы сегментации — что и есть контракт совместимости, ради которого sudachi.rs существует?

- **Path A — сохранить паритет с Java.** Оптимизировать решётку без изменения ни байта вывода.
- **Path B — сменить парадигму.** Заменить решётку pointwise-сегментацией (Vaporetto) + словарным
  feature-lookup. Сильно быстрее, но вывод больше не Java-Sudachi-овский.

Обе реальны и измерены. Дальше — честные плюсы и минусы каждой.

## Коротко (at a glance)

| | **Path A — сохранить паритет** | **Path B — смена парадигмы (pointwise)** |
|---|---|---|
| Вывод vs Java Sudachi | **идентичен** (A/B/C, POS, границы) | **другой**: одна сегментация, −0.92 SEG, −1.74 POS, нет A/B/C |
| Скорость 1-thread | **потолок ≈ 1.4–1.6×** (#39/#40 + #52 WordInfo-cache: +27% default / +44% full `-a`; ядро решётки на полу) | **~78 ns/char = ~3.7×** (реальный fused, тёплый кэш) |
| Рычаг throughput | **multithreading ~8.9×** (ортогонально, совместимо) | тоже параллелится; pointwise масштабируется чисто |
| Усилия | **малые** — зашипить готовое | **большие** — новый токенизатор + пайплайн обучения |
| Поддержка | нет (всё из словаря) | **переобучать ~58 MB модель под словарь** |
| Риск | **нет** (byte-identical, доказано) | **высокий** (слом compat + сопровождение модели) |
| Место *внутри* sudachi.rs? | **да** | **нет** — отдельный несовместимый инструмент |

## Path A — Сохранить паритет с Java-Sudachi (оптимизировать решётку)

**Что это.** Текущая архитектура: common-prefix search по double-array trie + Viterbi по матрице
связности 71 MB. Оптимизировать без изменения вывода.

**Плюсы**
- **Byte-identical с Java-Sudachi** — A/B/C, POS, границы сохранены. Контракт совместимости не тронут;
  воспроизводимость между Rust/Java/Python держится.
- **Нулевой риск, малые усилия.** Выигрыши уже собраны и доказаны byte-identical: prefetch (+16.7%),
  varint (+2.7%) и два переноса этого исследования — #39 (gate per-node `normalized_form`-декода в
  JoinNumeric) и #40 (early-out переменной секции WordInfoParser), вместе **~+9%** (320→294 ns/char),
  проверено по режимам A/B/C на двух корпусах.
- **+ #52: share `WordInfo` data+strings через `Arc` + bounded tokenizer-local cache = +27% на
  default-выводе, +44% на полном `-a`-выводе** [meas, реальный SudachiDict, GSD], byte-identical
  (A/B/C × 2 корпуса, diff = 0). Материализация WordInfo (parse + resolve + UTF-16-декод строк)
  отыгрывается дешёвым shared-доступом (два Arc-refcount) вместо повторного парса/декода на каждое
  вхождение. Выигрыш растёт с объёмом материализуемого вывода, т.к. делятся и декодированные строки.
  Самый крупный одиночный byte-identical рычаг (прежняя оценка прототипа была +20–21%).
- **Multithreading — реальный рычаг throughput, ~8.9×, ортогонален и совместим.** Складывается поверх
  1-thread-выигрышей и не меняет вывод.
- **Теперь точно известно, где пол** (усилия не тратятся зря): 18-агентный микроарх-разбор доказал, что
  матрица связности **L2-резидентна, не DRAM-bound** (live working set 3.77 MiB, 0 capacity-misses,
  97.95% L2-хитов; сама матричная загрузка = ≤7.2% do_tokenize), кодген оптимален. Ядро `connect_node`
  на полу.

**Минусы**
- **1-thread потолок ≈ 1.4–1.6×** (#39/#40 + #52 над зашипленным; верхняя граница — полный `-a`-вывод).
  Решёточное ЯДРО (`connect_node`/матрица) на полу — оно не рычаг; крупное нашлось в материализации
  WordInfo (#52). Сверх этого остаток размазан (trie — как уложен — на byte-indexed полу для
  добавленного prefetch, но корпус-частотный relayout двойного массива из #117 НЕ прототипирован
  и остаётся открытым; OOV; аллокации) — дальше
  архитектурная хирургия ради нескольких %.
- **Прирост throughput требует потоков.** Если нагрузка одно-поточная и latency-bound, Path A у предела.

**Итог:** безопасная, корректная дорога. Зашипить #39/#40 **+ #52** (+27–44% от кэша WordInfo, byte-identical),
опереться на multithreading, ядро решётки не трогать.

## Path B — Сменить парадигму (Vaporetto pointwise + словарь)

**Что это.** Убрать решётку. Vaporetto (pointwise линейная классификация, от Works Applications)
сегментирует и POS-тегирует за O(n); каждый сегмент затем ищется в словаре Sudachi для восстановления
`normalized_form` и POS-кандидатов. Реальный fused-бинарь (`/tmp/vapo-sud`) делает ровно это.

**Плюсы**
- **~3.7× быстрее на полной задаче** (seg + POS + normalized): **~78 ns/char vs ~290** [meas, реальный
  fused-бинарь, тёплый surface-кэш]. Робастно 71–113 ns/char на GSD-test/dev и новостях (kyoto-leads).
- **Сильно проще, меньше hot-path:** нет матрицы 71 MB, нет решётки, нет Viterbi. O(n) pointwise-работа,
  которая векторизуется и параллелится чисто (per-thread feature-кэш масштабируется 8.6–9.5× на 12 ядрах).
- **Переиспользует существующий словарь** для восстановления фич — exact-lookup лексикона и резолв
  `normalized_form` уже есть; новы только сегментатор и дизамбигуация POS.

**Минусы**
- **Ломает совместимость с Java-Sudachi — решающий.** Это не быстрый Sudachi, это *другой токенизатор*.
  Конкретно:
  - **Нет A/B/C.** Pointwise даёт одну сегментацию; мультигранулярные сплиты исчезают — главная фича
    Sudachi, дисквалифицирующая для любого потребителя, который их использует.
  - **Другой вывод даже там, где хорош:** −0.92 SEG-F1, −1.74 POS-top vs словарная решётка, т.е.
    воспроизводимость против Java/Python Sudachi теряется.
- **POS нужен гибрид, иначе плохо.** Брать первую запись словаря = POS-top ≈ 70 (омограф-ловушка);
  нужно держать предсказанный Vaporetto-POS для дизамбигуации кандидатов словаря (→ 95.7). Пайплайн
  требует *оба* сигнала — больше движущихся частей.
- **Операционная нагрузка:** отдельно обученная ~58 MB модель, переобучаемая при каждом изменении
  словаря (решётка же выводит всё из словаря бесплатно).
- **Скорость зависит от кэша.** ~3.7× предполагает тёплое повторение поверхностей (batch/индексация).
  На холодном или разнородном коротком входе per-token recovery растёт с ~7 до ~110 ns/char, и выигрыш
  сжимается.

**Итог:** реальная и существенная скорость, но меняет продукт. Может жить только *вне* обещания
совместимости sudachi.rs — как отдельный инструмент для тех, кому Java-паритет явно не нужен.

## Бок о бок: плюсы и минусы, которые решают

| измерение | Path A (паритет) | Path B (парадигма) |
|---|---|---|
| Совместимость с Java-Sudachi | ✅ идентично | ❌ сломана (нет A/B/C, др. seg/POS) |
| A/B/C-мультигранулярность | ✅ да | ❌ нет (одна сегментация) |
| Скорость (1-thread, полный вывод) | ➖ потолок ~1.4–1.6× (#39/#40+#52: +44% на полном `-a`) | ✅ ~3.7× |
| Throughput на масштабе | ✅ ~8.9× потоками | ✅ тоже хорошо масштабируется |
| Качество vs gold | ✅ SEG 97.99 / POS 97.46 | ➖ SEG 97.07 / POS 95.72 |
| Усилия на внедрение | ✅ малые (зашипить готовое) | ❌ большие (новый путь + обучение) |
| Текущее сопровождение | ✅ ничего сверх | ❌ переобучать модель под словарь |
| Риск | ✅ нет (byte-identical) | ❌ высокий (compat + модель) |
| Место в sudachi.rs | ✅ да | ❌ нет (отдельный проект) |

## Как читать trade-off

- **Если совместимость с Java-Sudachi обязательна** (контракт sudachi.rs): **только Path A.** Зашипить
  #39/#40 + #52, throughput — потоками, ядро решётки не трогать (на полу — доказано, с регрессионным стражем:
  nomat-проба + LRU-sim). 3× «как sudachi.rs» недостижимо; это пол.
- **Если нагрузке реально не нужны A/B/C или точный Java-вывод** (throughput-bound, SUW-only
  индексация/поиск): **Path B реален и ~3.7×** — но как *отдельный* инструмент, не библиотека.
  Запускаемый прототип и числа готовы к передаче.
- **Наиболее вероятный верный исход:** Path A для sudachi.rs (зашипить byte-identical-выигрыши +
  задокументировать пол, чтобы матрицу не пересматривали снова), Path B держать на полке как измеренную
  опцию на случай, если несовместимый быстрый токенизатор когда-нибудь понадобится.

## Доказательства и воспроизведение

```bash
# Path A — byte-identical-выигрыши + floor-proof
#   #39/#40 переносы: optimization-study.md §5.6-5.7 (worktree /tmp/sud-vib)
#   доказательство «матрица на полу» (L2-резидентна, nomat-проба + LRU-sim): §5.11
SUDACHI_BENCH_SUBSET=min SUDACHI_BENCH_MODE=C cargo run --release --example tokenize_pipeline_bench

# Path B — реальный fused-пайплайн: скорость (3 варианта) + качество
cd /tmp/vapo-sud   # vaporetto 0.6.5 + sudachi path-dep
VAPO_MODEL=/tmp/vapo/model.raw SUDACHI_BENCH_CONFIG=<full>/sudachi.json \
  SUDACHI_BENCH_DICT=<full>/system_full.dic SUDACHI_BENCH_INPUTS=/tmp/gold/gsd_text.txt \
  cargo run --release                            # тайминг: vaporetto-only / fused / fused+cache
VS_MODE=dump cargo run --release > /tmp/gold/fused_out.txt
python /tmp/gold/score_fused.py                  # SEG + POS (model / dict-first / hybrid) + normalized
```
